# Regras de trabalho Codex e OpenCode

## Protocolo permanente do ERP

Codex, OpenCode e qualquer outro agente de desenvolvimento devem consultar o
[protocolo do Projeto Diretor](docs/projeto-diretor/README.md) e as especificações
e referências aprovadas do módulo antes de iniciar uma tarefa.

1. Existe um único ERP Néia Salgados oficial. Continuar o desenvolvimento no
   ERP existente e preservar todos os layouts e funcionalidades aprovados.
   É proibido reiniciar o ERP, criar versões paralelas para aprovação ou
   substituir funcionalidades aprovadas.
2. O único endereço oficial de homologação é o definido abaixo. Usar a branch
   `resgate-visual-h01-h07-codex`, o Supabase `lflzlcqinarrcgncafol` e
   `VITE_DEMO_PREVIEW=0`. O modo demonstração é proibido na homologação.
3. Trabalhos paralelos usam branches e worktrees isoladas. Coordenar as
   integrações, migrations e publicações. São proibidas migrations simultâneas
   no mesmo banco e publicações conflitantes. Integrar na branch oficial
   somente depois de conferir a base atual, as mudanças em andamento e os conflitos.
4. Antes de publicar, executar os testes de regressão pertinentes e validar o
   ambiente. Conferir a versão publicada no endereço oficial e aguardar a
   aprovação manual do proprietário. Registrar cada etapa aprovada com
   documentação, commit e checkpoint versionado.
5. A produção usa o Supabase `ruioyioynwwwiqbjznoa` e permanece protegida.
   Toda alteração em produção depende de autorização expressa do proprietário.

### Isolamento de ambientes (P0 — 26/11/2026)
- Toda escrita ou migração remota exige destino declarado em `--project-ref`
  ou `NEIA_PROJETO_ALVO` e deve passar pela barreira
  `scripts/ambiente-seguro.mjs`.
- `supabase --linked` sem `--project-ref`, o `.env` e variáveis herdadas do
  terminal **não** são autoridade de destino. Divergência, produção ou dúvida
  bloqueiam a operação antes de qualquer conexão.
- Desenvolvimento e homologação usam exclusivamente `lflzlcqinarrcgncafol`.
  Banco local, projeto desconhecido e projeto legado também são recusados.
- Produção (`ruioyioynwwwiqbjznoa`) é somente leitura; qualquer alteração
  depende de autorização expressa, janela combinada e registro documental.
- Migração aplicada por SQL direto exige reconciliação de histórico
  documentada. Nunca reaplicar a migração para "consertar" o histórico.
- Comandos: `npm run seguranca:destino`, `npm run teste:seguranca`,
  `npm run sql:homolog`, `npm run build:homolog`.
- Norma completa e registro do incidente:
  `docs/projeto-diretor/seguranca-ambientes/`.

### Regras de publicação e versionamento
- Utilizar sempre o mesmo endereço de homologação; não criar novos projetos ou endereços.
- Sincronizar o GitHub antes de iniciar qualquer etapa e salvar os commits após cada implementação.
- Preservar os módulos aprovados.
- Validar o ambiente antes de publicar.
- Bloquear a publicação se houver referência ao banco de produção (`ruioyioynwwwiqbjznoa`) ou se o modo demonstração estiver ativado (`VITE_DEMO_PREVIEW=1`).
- Nunca usar force push.

## Preservação
- Não reconstruir o ERP sem autorização.
- Preservar layouts, fluxos e funcionalidades aprovados.
- Não apagar arquivos desconhecidos, modificados ou não rastreados.
- Não usar `git reset --hard`, `git clean`, `git stash` nem operações destrutivas sem autorização específica.

## Ambientes e segurança
- Production é protegida. Não fazer deploy, migration ou alteração no Supabase real sem autorização expressa.
- Usar dados demonstrativos nas prévias locais e isoladas de desenvolvimento, quando aplicável, e manter os scripts de proteção ativos. Na homologação oficial, usar somente o Supabase de homologação, com `VITE_DEMO_PREVIEW=0`.
- Não imprimir credenciais nem incluir segredos em arquivos versionados.

## Controle de versão
- Trabalhar na branch e worktree designadas. Não alterar `main` nem fazer push automaticamente.
- Criar commit local quando a etapa estiver aprovada ou houver autorização específica.
- Preparar arquivos seletivamente e revisar todo o diff antes do commit.

## Layouts e legibilidade
- Administração usa preto/grafite com dourado. A área pública preserva sua identidade aprovada. O App Motoboy segue a referência oficial com logomarca Néia Salgados.
- Priorizar legibilidade, contraste e alertas operacionais claros.
- Evitar CSS global que altere áreas não relacionadas.

## Menu lateral aprovado (P0 — 26/11/2026)
- `AdminShell`/`MenuLateral` é o padrão obrigatório e a fonte única do menu lateral em todos os módulos administrativos. Não criar menus independentes nem substituir ou duplicar manualmente o componente compartilhado.
- O menu publicado no commit `07b96de` foi aprovado definitivamente pelo proprietário no endereço oficial de homologação. A aprovação cobre exclusivamente o menu lateral; não autoriza alterações em painéis internos, rotas, permissões, banco, produção ou deployments.
- A paleta oficial, os 224 px de largura, os grupos, o item ativo, o cabeçalho da logo e o rodapé do usuário são aprovados e preservados. Não alterar cores, tokens, estrutura ou identidade visual sem autorização expressa do proprietário.
- Toda alteração nesse menu exige autorização expressa, nova conferência manual, atualização da documentação de aprovação e novo checkpoint versionado. Referência: `docs/projeto-diretor/menu-lateral/status.md`.

## Autonomia e limites
- O agente pode examinar o código relevante, implementar dentro da etapa aprovada, corrigir erros comuns, executar testes locais, investigar build, preparar relatórios e gerar Previews locais seguros.
- Não interromper por erros técnicos comuns. Interromper diante de risco de perda de dados, alteração em Production ou banco real, mudança de regras financeiras/comerciais aprovadas, necessidade de credenciais ou permissões amplas, mudança substancial de layout, conflito Git com risco de sobrescrita ou falha de segurança sem solução comprovada.

## Economia de créditos
- Não repetir auditorias concluídas nem analisar áreas fora do escopo.
- Reutilizar componentes existentes e evitar execuções repetidas sem motivo.
- Relatar resultados, mudanças e pendências de forma concisa.

## Responsabilidades
- Codex cuida de Comercial, integrações complexas, segurança e testes de integração.
- OpenCode cuida do App Motoboy na worktree independente e das tarefas designadas.
- Não editar simultaneamente os mesmos arquivos nem integrar mudanças entre worktrees sem autorização.

## Entregas
- Cada etapa registra funcionalidade, testes pertinentes, resultado visual quando aplicável, arquivos alterados, Git status e pendências reais.
- Uma demonstração não caracteriza a funcionalidade como operacional.
